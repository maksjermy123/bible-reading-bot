# 📖 План чтения Библии — Telegram Mini App

Мини-апп для бота **@mybible_reading_bot**: готовые и свои планы чтения Библии, трекер прогресса и дней подряд («стрик»), синхронизация между устройствами, напоминания.

Фронтенд полностью статический (GitHub Pages), бэкенд — **общий с проектом [MyRadio](https://github.com/maksjermy123/MyRadio)**, один и тот же процесс FastAPI на Render обслуживает и радио-бота, и этого. Подробности бэкенда, эндпоинтов и схемы Supabase — в README проекта MyRadio, раздел «📖 План чтения Библии».

---

## Архитектура

```
Пользователь открывает @mybible_reading_bot
        │
        ▼
GitHub Pages (index.html — весь мини-апп, один файл)
        │
        │  fetch к общему бэкенду MyRadio
        ▼
Render (main.py — репозиторий MyRadio, НЕ этот)
        │
        ▼
Supabase — bible_accounts, plan_progress
```

⚠️ **`main.py` и `Procfile` в этом репозитории — устаревший, неиспользуемый черновик.** Реальный бэкенд, который дёргает `index.html`, живёт в репозитории **MyRadio** и задеплоен как `myradio-rrsk.onrender.com` (см. переменную `BACKEND` в начале `index.html`). Если нужно поменять серверную логику — правьте `main.py` в MyRadio, а не здесь.

## Источник правды и синхронизация

Раньше это было три независимых, не связанных друг с другом хранилища — источник почти всех багов, которые ловили и чинили в этом проекте:

| Хранилище | Что содержит | Где живёт |
|---|---|---|
| `localStorage['bapp3']` | Полное состояние приложения на ЭТОМ устройстве | Браузер/WebView |
| `app_state` (Supabase) | Полный снимок того же состояния, для синхронизации между устройствами | Сервер |
| `plan_progress` (Supabase) | Канонический прогресс **по каждому плану отдельно** — стрик, дни, настройки напоминаний | Сервер |

Правила, которые не должны нарушаться при доработках:

- **Стрик и `days_done` всегда канонические с сервера** (`plan_progress`), а не из `localStorage`. `syncCanonicalDaysDone()` вызывается при каждом открытии для каждого плана и сливает (не перезаписывает) локальные и серверные данные через `/plan/merge_days`.
- **`checkAccountReset()`** — первая вещь, которая выполняется в `syncBackend()`. Сверяет локально сохранённый `reset_token` с тем, что вернул `/account/status`. Если они разошлись — значит аккаунт сбрасывали (`/users` в боте) с прошлой синхронизации этого устройства, и `localStorage` стирается ДО того, как успеет уйти `pushState()` и воскресить удалённые данные обратно на сервер. Без этой проверки удаление пользователя в боте не удаляло данные по-настоящему — старый кэш на устройстве просто заливал всё обратно при следующем открытии.
- **`markRead()` не должен разрушать локальный прогресс при сбое записи.** Если сервер отвечает `{"ok": false, "error": "not registered"}` (например, из-за временного сбоя сети, а не только реального удаления) — код один раз тихо перерегистрирует план и повторяет попытку, вместо того чтобы удалять план целиком. Более ранняя, более агрессивная версия этой проверки удаляла план при любом сетевом сбое — так пропадал второй параллельный план при обычной сетевой заминке.
- Индикатор **`⚠️ не синхронизировано`** (правый верхний угол, `syncBadge()`) загорается при любом сетевом сбое синхронизации (не только "not registered") — раньше все такие ошибки проглатывались молча, и человек мог неделями не знать, что его прогресс не сохраняется на сервере.

## Планы чтения

### Встроенные (`PLANS`)

Захардкожены в `index.html`, у каждого готовое `schedule` — массив дней с `refs` (книга/глава/стихи) и `label`.

### Свой план (конструктор, `pg-con`)

Пользователь выбирает книги и срок в днях → `buildCustomSchedule(days)` строит расписание, равномерно распределяя суммарное число стихов по дням (может дробить главу пополам, если нужно для баланса).

### Хронологический Новый Завет (адаптивный)

Не «запечён» на фиксированное число дней. Вместо этого:

- `NT_CHRONO_U` — компактный список из 380 «юнитов» чтения (книга/глава/стих_от/стих_до) в хронологическом порядке (гармония четырёх Евангелий → Деяния → Послания по времени написания → Откровение), ~4 КБ данных, без текста — только ссылки.
- `buildChronoSchedule(days)` разворачивает юниты в плоский список из 7955 стихов и нарезает на **любое** число дней, которое укажет пользователь, — тем же алгоритмом равномерного распределения, что и обычный конструктор.
- Хранится как обычный `customPlans` с меткой `chrono:true` — весь остальной механизм (стрик, синхронизация, напоминания, редактирование) работает для него без отдельного кода.

Реальное название плана (включая сгенерированное, например «🕰️ Хронологический Новый Завет · 56 дней») отправляется на сервер при регистрации и самовосстанавливается при каждом открытии через `/plan/merge_days` — важно для напоминаний и для виджета «План» в мини-аппе Radio, которые иначе показывали бы обезличенное «Свой план» для любого не-системного плана.

## Несколько планов параллельно

Поддерживается по конструкции: `app.progress` — словарь `plan_id → прогресс`, не единственное значение. У каждого плана свои: стрик, `days_done`, время и вкл/выкл напоминаний (`notify_hour_msk`/`notify_minute_msk`/`notify_on` — per-plan, не глобально).

На сервере это работает, только если в `plan_progress` уникальность задана как `UNIQUE (user_id, plan_id)`, а НЕ `PRIMARY KEY (user_id)` — при последнем варианте второй план для того же пользователя физически не может стать отдельной строкой (реальный баг, который ловили: второй план молча пропадал сразу после регистрации).

## Диплинки

Мини-апп реагирует на два способа передать намерение «открыть именно этот план» при запуске:

| Параметр | Где взять | Пример |
|---|---|---|
| `?plan=<id>` в самом URL | `location.search` — прямые `web_app`-кнопки (уведомления бота) | `index.html?v=123&plan=bible_365` |
| `startapp=open_<id>` | `tg.initDataUnsafe.start_param` — кросс-ботовые `t.me/...`-ссылки (виджет «План» в другом мини-аппе) | `t.me/mybible_reading_bot/plan?startapp=open_bible_365` |
| `startapp=wipe` | `tg.initDataUnsafe.start_param` | `t.me/mybible_reading_bot/plan?startapp=wipe` — принудительно стирает `localStorage` на этом устройстве до загрузки приложения (ручной админский/отладочный сценарий) |

## Безопасность

Все сетевые вызовы (кроме `GET /plan/status`, которого этот мини-апп даже не использует напрямую) передают `tg.initData` (`init_data` в теле/query) — сервер проверяет HMAC-подпись именно ботом @mybible_reading_bot и сверяет `user_id` из подписи с тем, что указан в запросе. Раньше любой, кто знал чужой Telegram ID, мог менять/удалять чужой прогресс через прямой вызов API.

## UI-детали

**Ползунок размера шрифта** (вкладка «Настройки») реагирует на перетаскивание пальцем/мышью по всей полоске (`initFontSlider()`, Pointer Events с фолбэком на touch-события), а не только на кнопки `A−`/`A+`. 5 фиксированных размеров (`FS`), индекс пересчитывается в реальном времени по ходу движения.

**Копирование текста** — два независимых способа:
- Тап по цифре стиха (`copyV()`) — быстрое копирование одного конкретного стиха.
- Выделение текста пальцем/мышью (стандартный жест, как в любом читалке) — при непустом выделении внутри `.st` всплывает кнопка «📋 Копировать» над выделением (`initSelectionCopy()`, слушает `selectionchange`), копирует именно выделенный текст. Работает поверх нативного выделения браузера, ничего не подменяет.

## Локальная разработка / деплой

Правки в `index.html` — просто коммит в `main`, GitHub Pages подхватывает автоматически (обычно 1–2 минуты). Никакого шага сборки нет — это чистый HTML/CSS/JS в одном файле.

При деплое, затрагивающем и фронтенд (`index.html`, этот репозиторий), и бэкенд (`main.py`, репозиторий MyRadio) — оба нужно выкладывать вместе: фронтенд может начать слать поля (например, `init_data`, `title`), которые старый бэкенд ещё не умеет принимать, и наоборот.

Регистрация в BotFather — см. README MyRadio, раздел «Первоначальная настройка», шаг 7 (у бота @mybible_reading_bot свой отдельный Mini App с `short_name: plan`, URL — `https://maksjermy123.github.io/bible-reading-bot/`).
